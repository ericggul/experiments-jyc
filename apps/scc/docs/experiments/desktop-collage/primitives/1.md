# primitives/1 — heart of windows

Route: `/desktop-collage/primitives/1`, created 2026-10-05. Control endpoint:
`/desktop-collage/primitives/1/control`. Implementation:
`components/desktop-collage/primitives/1/`.

## Tested relation

One button opens 20–30 real windows (Chrome app windows by default). Each window is a
plain rectangle, and the windows' centres follow a heart outline, centred
horizontally and vertically on the desktop. The question is whether a figure can
emerge from browser windows as raw material, and how the rhythm of their arrival
(one by one at 0.1 s, or all at once) changes it.

## How it works

- **Measurement:** the Mac's main display and its visible frame (without menu
  bar and Dock) are read through AppKit on page load, whenever the control page
  regains focus, and again immediately before every run. The layout is always
  computed for the current desktop size.
- **Shape:** `model/heart.ts` samples the classic heart curve at equal arc
  length from the top cusp, then scales it so every window stays inside the
  visible frame. Centring uses the outline's bounding box.
- **Shared layout:** the same function draws the page preview and places the
  real windows, so the two always match.
- **Rhythm:** one JXA process opens every window on an absolute schedule
  (window i at i × interval), so slow window creation does not accumulate
  drift. "All at once" means no deliberate gap: windows still appear as fast as
  the browser can create them, which is not truly simultaneous. The result
  reports the measured first-to-last time.
- **Order:**
  - *trace* follows the outline clockwise from the cusp;
  - *both sides* grows the two halves symmetrically down to the tip;
  - *shuffle* uses a seeded order.
- **Surface**, in order of preference:
  - chrome app (default): only a thin title bar, no toolbar or tabs;
  - terminal: windows painted a flat colour;
  - bare: borderless.
- **Fill:** hot pink `#ff2e93`, red `#ff1a2e`, the two alternating around the heart, or (chrome app and bare only) a random Wikipedia article. Colour pages are self-contained data URLs.
- **In front:** sets which windows end up in front once they overlap: newest, oldest, upper or lower. Chrome app windows always keep the newest in front. Each new window takes its stacking rank as soon as it opens, so the stack is right throughout the sequence, not only at the end.
- "clear all" removes every window this page opened; by default each run clears the previous one first.

Parameters: windows 3–60 (default 30), interval 0.02–1 s (default 0.1), heart
size, and window width/height as a share of the visible desktop.

## Evidence and open questions

Checked so far:
- pure tests cover containment at several display sizes, centring, mirror
  symmetry, even spacing and order completeness;
- the JXA scripts compile with `osacompile`;
- the read-only display measurement returned 1470 × 956 with visible 1470 × 843
  from y = 38 on this Mac;
- typecheck and lint passed.

2026-10-05 feedback on the first version: the windows needed colour, and the
browser toolbar was far too thick. Safari offers no way to hide its toolbar in
a normal window; the only toolbar setting in its menus is "Always Show Toolbar
in Full Screen" (checked in Safari's `MainMenu.nib`). Terminal's title bar is
the thinnest chrome available, so Terminal is now an option.

Not yet observed: no windows have been opened. Unknown until the first run:
- the real cadence at 0.1 s;
- Safari's minimum window size (resized windows are counted and reported);
- how the heart reads once windows overlap;
- whether "all at once" looks simultaneous.

## 2026-10-05 trials of the surfaces

These were run through `foundations/runtime.ts` with screenshots.

| Surface | Result |
| --- | --- |
| bare (default) | No chrome at all. 30 windows at 0.1 s: first to last 2,903 ms against 2,900 planned. "all at once": 43 ms. WebKit pages render inside. Killing the host removes every window. |
| chrome app | Only a thin title bar, which stays grey (no tint). Needs three workarounds: a `First Run` marker, launching through `open -n`, and placement through the instance's local DevTools endpoint. With them: 30 windows exactly on the heart, 2,802 ms. Newest is always in front. |
| safari | Colour data URLs work and placement is exact; the toolbar cannot be hidden. |
| terminal | Exact placement and true colours. JXA takes 0–1 RGB; 16-bit values clamp and wash out. The title bar still shows the shell's process name. |

Chrome app problems found and fixed on the way:
- a fresh profile shows a modal welcome dialog that blocks new windows;
- windows handed to a running instance ignore the position and size flags, and
  stack at the first window's place;
- macOS ignores activation requested from a background process.

Launching Safari or Terminal opens the app's own default window. The open
script now closes it, but only when the app was not already running.

Not observed yet: a run started from the control page itself (these trials
call the same runtime directly).

2026-10-05, later: the surfaces were narrowed to chrome app (default), then
terminal, then bare. Safari and plain Chrome were removed; bare was judged
weaker and kept for other uses.
