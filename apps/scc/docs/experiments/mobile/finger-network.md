# Mobile finger-network/1

- **Route:** `/mobile/finger-network/1`
- **Date:** 2026-09-28
- **Baseline:** `finger-skating/default`'s captured-pointer, full-viewport canvas pattern.

Each active touch is a node at that finger's current position. Every pair of nodes has one white edge, so `n` fingers display the complete graph `Kₙ` with `n(n − 1)/2` edges. A small white dot, fixed ring, and repeating expanding ring make each node visible even when only one finger touches the screen. Captured document touch events update only their changed identifiers; ending or cancelling one contact removes only that contact. A window blur does not erase the whole graph. Safari gesture defaults are prevented where cancelable. Mouse and pen retain pointer input, with touch pointer events used only when Touch Events are unavailable. Releasing or cancelling a touch removes its node and all incident edges immediately.

The screen is black with no controls. A short instruction appears only while there are no active fingers. The canvas redraws while fingers are active and stops scheduling frames when all touches end; its pixel ratio is capped at 1.5. The code has no finger-count cap, but **more than five simultaneous contacts on one iPhone are unsupported**: [WebKit currently returns 5 for `maxTouchPoints` on iOS](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/Navigator.cpp), and [WebKit's implementation note says 5 matches the simultaneous touch count on iPhone while iPad can support more](https://trac.webkit.org/changeset/246070/webkit). The user observed that moving a second hand briefly formed the graph, then removed all nodes and restored the instruction. The exact event sequence behind that reset is unverified; Safari can [cancel touch points when capacity is exceeded](https://www.w3.org/TR/touch-events/#the-touchcancel-event). Further canvas or event-handler changes cannot reconstruct positions Safari does not deliver. Typecheck and diff checks passed; this is **not a verified fix** for two-hand or 10+ finger interaction on an iPhone.

For diagnosing a particular device, append `?touch-debug=1` to the route. The temporary overlay reports browser-exposed `navigator.maxTouchPoints`, the highest contact count actually delivered, cancellation count, and the last event. It does not appear on the normal route. The reported maximum can be a conservative or canned value, so the observed contact count is the stronger evidence for a particular device.

The contact-state model has a pure check for adding one five-finger hand, adding and moving a second five-finger hand without erasing the first, cancelling only one identifier, and accepting twelve supplied contacts. This establishes that the app's state code has no five- or ten-contact cap; it does not establish that a phone browser supplies those contacts. A verified one-phone hardware candidate for **exactly ten** contacts is the [ASUS ROG Phone 9](https://rog.asus.com/phones/rog-phone-9/spec/), whose published display specification says 10-point multitouch. Its browser behavior with this experiment, system gestures, contact spacing, and ten-person use have not been tested. No stock phone with more than ten certified simultaneous screen contacts has been identified here.

For acceptance on a ten-point phone, the diagnostic route must show `highest reported: 10` while both hands move, without a cancellation that removes held contacts; then the normal route must keep all ten nodes and 45 edges moving. On ROG Phone 9, the [ASUS support forum](https://zentalk.asus.com/t5/rog-phone-9/touch/td-p/478787) identifies the three-finger screenshot gesture as a possible competing system action, so it should be disabled during this check. These are verification criteria, not an observed result.
