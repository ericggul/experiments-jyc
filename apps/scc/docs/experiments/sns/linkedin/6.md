# LinkedIn 6 — 3D live-interface experiment log

- **Route:** `/sns/linkedin/6`
- **Canonical content:** `/sns/linkedin/2`
- **Required outcome:** every independently updateable LinkedIn component is its
  own high-fidelity 3D cylinder; the content itself, not a separate backing
  object, must occupy that cylinder surface. Orbit must remain mouse-driven.

## Rejected implementations — 2026-09-14

These are recorded to prevent reintroducing the same invalid structures.

1. **`foreignObject` SVG → `CanvasTexture`.** Rendering a source DOM clone into
   SVG and then drawing it into a canvas taints the canvas in Chrome. Three then
   throws `SecurityError` from `texSubImage2D`. Do not use this pipeline.
2. **One `Html transform` clone per narrow WebGL facet.** Drei CSS3D and Three
   pixel/world transforms do not share a stable unit mapping here. The result
   either sub-pixel text or overlapping, torn text. Do not tune this further.
3. **Billboarded `Html` strips.** These retain readable DOM but are camera-facing
   planes, so they cannot be the component's cylindrical surface.
4. **A full `2π` DOM strip cylinder.** Mapping the entire source width around
   360 degrees leaves only one narrow source strip facing the viewer; it does
   not preserve the readable initial interface.
5. **Front-arc DOM plus a separate Three cylinder.** This creates a flat DOM
   card inside/in front of a cylinder, rather than DOM = cylinder. It is not an
   acceptable representation and must not be extended.
6. **Hand-painted Canvas DOM surrogate.** It avoided taint but approximated CSS
   text, flex layout, and icons, so it could not preserve the reference DOM at
   pixel fidelity. It must not replace browser DOM paint.
7. **One full-page DOM atlas.** Capturing every post into one large texture
   made an otherwise static Orbit scene pay a multi-megapixel layout and paint
   cost before its first usable frame. It is not permitted for this route.

## Current renderer contract — 2026-09-14

- Each header, rail card, composer, sort control, post, right-rail card, and
  messaging dock is its own `PlaneGeometry` surface. Its two horizontal edges
  are vertex-mapped to the same point with a `2π` arc, producing one closed,
  full 360-degree cylinder per component—not a card plus a backing mesh.
- `LinkedinTwo` remains the live DOM/state owner. Each cylinder receives a
  direct, CORS-safe browser paint of only its own source component; UV clicks
  are mapped back to that source component and state mutations repaint only
  that component after a short debounce.
- Browser-paint capture is globally serialized. The entry scene prepares only
  the visible header, rail, composer, first posts, right card, and messaging
  surface. Other posts remain independent meshes and gain their texture only
  after they are visible when a control gesture ends. During an OrbitControls
  gesture both capture work and the eventual WebGL texture upload are held.
- Cylinders are horizontal-only deformations: 160 radial segments and one
  vertical segment. No per-frame mesh deformation, visibility polling, texture
  upload, or React state work occurs while OrbitControls is moving.
- `foreignObject` remains prohibited. Canvas capture must use CORS-safe input
  and reject tainted media rather than emitting a WebGL texture error.

## Constraint to resolve before a new renderer

A browser DOM tree is planar. A continuous WebGL cylinder needs a texture;
native CSS3D DOM can be spatially placed but not non-affinely deformed as one
continuous mesh. The next implementation must establish one rendering route
that preserves live source-state updates while mapping the content surface to
the cylinder, rather than combining the rejected DOM and backing-mesh routes.
